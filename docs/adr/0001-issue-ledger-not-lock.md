# ADR-0001：使用 GitHub Issue 作为协调账本，而不是锁

状态：已接受
日期：2026-09-04
决策者：项目维护者
影响范围：多 Agent 任务认领、状态同步、交接和验证

## 上下文

`dsh-compat-suite` 计划由多个 Agent 并行完成 `core`、CLI、dsh 插件、规则、schema、测试和发布工作。并行可以缩短交付时间，但也会引入重复实现、写入范围重叠、公共接口漂移、测试证据被覆盖和责任不清等风险。

GitHub Issue 能记录目标、依赖、assignee、label、评论、子任务和 PR 关联，但这些字段不能提供原子 compare-and-set，也不能阻止另一个身份或共享账号在同一文件上写入。把这些字段称为“锁”会产生错误安全感，并把网络、权限或自动化故障误解为互斥保证。

## 决策

1. GitHub Issue 是任务范围、认领请求、协调者确认、进度、阻塞、交接和完成状态的主协调账本。
2. Issue、label、assignee、Project、评论、分支、worktree 和本地文件都不被定义为锁。
3. 不实现仓库内 claim lockfile、文件锁、数据库租约或必须在线的中央锁服务。
4. 正常协作仍采用 fail-closed 流程：没有协调者的 `CLAIM_CONFIRMED` 记录，Agent 按协议不得写入。
5. “一个 Issue 一个活跃实现 Agent”和“不允许重叠写入范围”由参与者与协调者共同执行，而不是由平台强制。
6. 时间字段只用于识别陈旧认领；超时不会自动转移任务，必须经过分支、PR 和工作状态复核。
7. label、assignee 和 Project 字段是便于查询的派生视图；发生不一致时，以 Issue 正文和最新有效协调事件为准。
8. 所有更正、转交和状态变化使用新评论追加，避免通过编辑旧评论静默改写历史。该约束是流程惯例，不把 GitHub 评论误称为不可变审计日志。

## 理由

- 任务协调需要可读、可链接、可评审的长期记录，而不是低层互斥原语。
- Git 分支和 worktree 已提供内容隔离；额外锁服务会引入可用性、恢复和权限复杂度。
- 锁无法解决语义冲突，例如两个不重叠路径同时修改同一个 report schema 的含义。
- 显式范围、共享接口、确认和交接记录更适合人类与异构 Agent 混合协作。
- 不声称互斥，可以迫使验证覆盖竞态、陈旧状态和违规写入后的恢复路径。

## 被拒绝的替代方案

### 仓库内 claim 文件

拒绝把 `.agents/claims/*.lock` 或类似文件提交到 Git。多个分支可能同时创建相同 claim，合并延迟会让状态陈旧，清理也可能误删仍有效的工作记录。

### 把 assignee 或 label 当作锁

拒绝。字段更新可能并发、延迟、失败或被有权限的人覆盖；共享 GitHub 账号也无法仅靠 assignee 区分 Agent 实例。

### 中央数据库或租约服务

MVP 拒绝。它会成为额外信任根和单点故障，需要身份认证、原子事务、续约、恢复和运维，超过当前项目收益。

### 完全不做认领记录

拒绝。仅靠聊天或分支名无法稳定表达非目标、依赖、写入范围、共享接口和交接证据。

## 结果与代价

正面结果：

- 协作状态集中在可关联 Issue/PR 的位置；
- 人类和不同 Agent 可以采用同一格式；
- 不依赖额外服务即可启动；
- 故障后可根据记录、分支和验证证据恢复。

代价和限制：

- 协议不能物理阻止两个 Agent 同时写同一路径；
- 协调者需要检查范围和共享接口；
- 参与者违反协议时仍可能产生冲突；
- GitHub 不可用时，正常模式下不能发起新写入；
- 共享账号下的 `agent_id` 是协调标识，不是密码学身份。

## 安全与隐私

- Issue 中不得粘贴 token、credential、真实 DSH session、插件 storage 或未脱敏进程管理器/服务监督器日志（例如 PM2 日志）。
- Issue Form 和未来自动化不得把自由文本直接拼接为 shell 命令。
- fork PR 和外部 Issue 内容视为不可信输入。
- 协调记录不授权扩大产品扫描范围，也不改变 CLI/插件默认只读边界。

## 验证

G1 必须证明：

- 同一 Issue 的两个并发请求只产生一个有效确认记录；
- 协议能发现路径和共享接口重叠，并要求未确认方停止；
- 不重叠任务可以在独立 worktree 中并行；
- 超时、转交和异常中止不会自动把任务交给另一 Agent；
- 模板和文档中不存在“已锁定”“自动互斥”等误导性承诺；
- 仓库中不存在 claim lockfile 或依赖中央锁服务的实现。

完整方案见 [`../06-multi-agent-collaboration.md`](../06-multi-agent-collaboration.md) 和 [`../04-validation-plan.md`](../04-validation-plan.md)。

## 重新评审触发条件

只有出现以下情况之一才重新评估锁服务：

- 并发规模持续导致无法由范围拆分和协调者复核控制的高频冲突；
- 自动化写入主体需要跨仓库原子操作；
- 合规要求需要比 GitHub 时间线更强的不可变审计或身份保证；
- 已有平台提供可验证、可恢复且维护成本可接受的事务式认领 API。

即使未来增加技术互斥，也必须保留 Issue 账本、范围声明、共享接口检查和交接记录。
